# 红蝶：围绕具体疑点的核验 · 2026-10-26

本轮将新开「红蝶陷阱」的全部 8 个普通调查对象改为专属核验。玩家选择要检验的问题，系统继续负责专业检测、证据匹配及结案裁定。其余七案维持现有核验内容；本轮没有推送或部署。

## 玩家可见变化

| 对象 | 可先取得的初步发现 | 完整核验进一步检验 |
| --- | --- | --- |
| 3 号舱诊断口 | 保险触点和机械部件状态 | 本次功率与保护指令实际执行 |
| 消息缓存 | 重复付款提醒之间的联系 | 原始消息、签章和完整上下文 |
| 后台门禁 | 排班与权限使用时段的冲突 | 独立门侧影像及读卡时钟 |
| 控制平板 | 残留控制片段和副本校验值 | 批准、部署与设备执行记录 |
| 目击录音 | 停顿前后的实际方向描述 | 原始来源和完整目击段落 |
| 芯片箱 | 数量、编号、标签与焊点 | 实物功能、标准型号与供货单 |
| 酒杯残留 | 与正常酒样不同的成分 | 杯号封签及独立配液记录 |
| 包厢终端 | 单笔记账的证明范围 | 连续记录能覆盖的在场区间 |

每个对象展示疑点和三种方法的检查范围。有效初查保存双语结果与「证明局限」，不因尚未取得关键证据而增加失败混乱。初步发现不会自动成为报告证据，也不会解锁入口、剧情后段、人物对峙或专属核验。完整核验保留原证据 ID、结论及区域入口动作。

初查和后续完整核验按同物件实际付过的 AP 抵扣，基础费用合计最多 1 AP。已经由技能免除的 AP 不再产生抵扣；抵扣不可跨物件或用于不适用的方法，优先于其他免 AP 额度。每次新检查仍消耗报价中的体力并推进一回合，因此多做初查会增加时间和危机暴露。

已做的检查可跨探员、跨语言免费复查，不推进回合、不恢复体力、不重复发证据或技能奖励。完整核验后仅保留完整结果与此前已取得的初查复查入口，不免费生成尚未进行的检查。

## 兼容与保密

- 仅新建 V2 红蝶运行写入 `inspection_revision: 1`。缺少标记、未知标记、其他案件与 V1 均保留原判定。
- 不提升 `case_design_revision`，不改变现有付费案件的内容版本和结算规则。状态存入原 `run_json`，没有数据库迁移。
- `inspection_findings` 保存已取得的初查记录；公开投影仅包含方法名称、结果、局限和执行探员，不包含支付记账或未选方法的结果。
- 完整证据、专业注释、来源提示及报告支持映射仍按原取得条件发布。客户端只提交报价绑定的 `option_id`，不可提交价格、结果或执行人覆盖字段。
- 沿用 revision、操作去重和会话事务。新增回归覆盖旧报价、重复提交、保存恢复、资源不足原子拒绝及零 AP 抵扣执行。
- 生产包私有文本审计新增 8 个对象的初查结果、局限及失败解释，覆盖 1,470 条私有文本；22 个浏览器 JS 文件中零命中、零服务端越界导入。

## 验收记录

- 八对象真实可通行路径：全部先初查再完整核验，合计 8 AP、16 回合；初查前后入口、剧情和关键证据保持一致，补核验后才按原规则推进。
- 最低能力与默认队伍的红蝶主线仍为 15 AP、15 回合，完成 8 份核心证据、6 次证词进展与专属核验，B 级结案；替代解释及隐藏旁证测试可达到 S。
- 全初查路线另做两组完整通关：保留自然危机调度、逐次选择公开的 0 AP 应对选项，最低能力和默认队伍均消耗 15 AP、23 回合、B 级结案；不是零后果通关。最低能力结束混乱 11、信誉 95，默认队伍混乱 16、信誉 100。序列化存档分别 31,736/31,353 字节，恢复后结案及已结算状态重判均通过。
- 原难度压力用例保留：20 AP 支持完整调查、一次真正不适用的方法、两次各 2 AP 的保全危机和一次证据补正。测试从当前版本选取不适用方法，不再错误地把有效初查当成失败。
- 实际浏览器使用一次性本地内存案件，后端调用真实 `applyRunCommand`，前端使用实际现场面板。键盘执行初查后：AP 19、回合 1、证据 0，后台入口关闭；刷新后免费复查维持相同资源与体力；补核验后：AP 19、回合 2、证据 1，后台入口开放。
- 中英文界面和 390px 窄屏均检查，文档宽度 386px，没有整页横向溢出；测试页控制台无错误。截图：`/tmp/td-inspection-desktop-20261026.png` 与 `/tmp/td-inspection-mobile-20261026.png`。
- 临时测试服务与页面已清理，没有访问生产账号，也未改动用户原本的 5177 服务。这不是生产登录端到端测试或实机 GPU 测量。

最终 `npm test`：1,318 项通过，零失败、零跳过。类型检查、Lint、安全检查（549 个源文件及 Git 历史）、生产构建、Worker dry-run、私有文本审计和 `git diff --check` 均通过。构建仍有既有 3D 大分块提示；完整 Cloudflare 发布预检仍需本地 Firebase 前端配置，Worker dry-run 不等于发布预检通过。

## 后续边界

本轮覆盖一案的完整核验样板，不代表其余七案已经采用多种有效方法。初步发现目前供现场复查，不可单独用于报告或推理连线。下一轮扩展前应观察玩家是否能解释「取得了什么事实、还缺什么证明」，而非只统计是否选中完整方法。
